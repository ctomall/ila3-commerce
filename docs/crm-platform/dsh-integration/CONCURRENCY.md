# 在线人数 与 并行 AI Run：定义、实测基线、待定目标

日期：2026-11-12 · 运行 release：`8d42e12`（生产） · 脚本：`scripts/crm-concurrency-baseline.mjs`

## 1. 两个数不是一回事

| 指标 | 定义 | 怎么测 | 现状 |
| --- | --- | --- | --- |
| 在线人数 | 一个时间窗内有有效 CRM 会话的用户数 | 会话/心跳计数（本次**未测**） | 没有产品目标，也没有采集口径 |
| 并行 AI Run | 同一组织内**同时执行** DSH 的助手 Run 数 | 同时发起 N 个真实 Run，读流与 `dsh_runs` 行 | 已实测基线（下节） |

“在线”不代表在跑模型；“并行 Run”也不等于在线人数 × 1。两者必须分开定目标、分开压测。

## 2. 实测基线（不是目标，不判通过/失败）

命令：`node scripts/crm-concurrency-baseline.mjs --n 2`
证据：`evidence/concurrency-baseline-2026-11-12T06-32-00-441Z.json`

| 场景 | 结果 |
| --- | --- |
| 单人单 Run | HTTP 200，首字节 6.2s，总耗时 7.8s，输出含 `OK` |
| 同员工并发 2 个 Run | **1 个 200**（首字节 1.6s，总 2.9s）；**1 个 409 `run_in_progress`**（307ms 拒绝） |
| 并发墙钟 | 2.9s（第二个没有排队等待，直接被设计拒绝） |
| 运行后 | `activeRuns=0`；`dsh_runs` 分布 cancelled/completed/failed；`customer_entities` 9→9 无写入 |

**结论（当前架构）**：每名员工同时只允许 **1 个** AI Run；第二个并发请求按设计返回 409，不排队、不静默丢失。
所以“并行 AI Run”的当前容量是“员工数 × 1”，但组织/租户层面的总并发还受 DSH 子进程、Unix 用户与主机资源约束，本次只测单员工维度。

## 3. 目标：未定，需要产品口径

以下只是**建议选项**，不是已确认目标，也没有据此判过任何验收：

- 方案 A（保守）：维持每员工 1 个活动 Run；组织并发目标按“同时使用助手的员工数”评估；
- 方案 B（排队）：第二个 Run 进入队列并给出 `queued` 状态与位置，而不是 409；
- 方案 C（提高单员工并发）：允许每员工 N 个 Run，需要先解决同一 home/workspace 与凭据共享的隔离问题。

在线人数的目标同样需要口径（按日活、15 分钟活跃、还是会话数）。

## 4. 复测方式

```
node scripts/crm-concurrency-baseline.mjs --n 2        # 写 evidence/concurrency-baseline-*.json
```

脚本只做短提示词（一次几十 token），不写 CRM 业务数据；`--n` 上限 4，避免把生产压出真实故障。
