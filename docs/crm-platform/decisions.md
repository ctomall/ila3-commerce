# 待决清单 · 需要用户拍板

规则：**未定项不静默猜**。每项给出「为什么必须定」「不定会怎样」「我建议的默认」，用户点头即冻结为规则并写进对应设计文档。

## D1 报价转订单的溯源语义（阻塞既有功能）

- 现状：`convert_to_order` 会把源报价单**物理删除**，`sales_orders` 没有 `quote_id` 列。
- 为什么必须定：订单无法回溯到报价，审计与对账断链；后续任何「报价 → 合同 → 订单」都要踩着这个决定。
- 不定会怎样：M5 的「获客 → 报价 → 订单」链路里，报价环节是不可追溯的断点。
- 建议默认：**保留报价单并标记 `converted`，订单写入 `quote_id`**（迁移只生成 SQL，应用前另行申请）。

## D2 候选入库的去重键与归属冲突

- 需要定：公司级去重用什么（根域名 / 税号 / 名称+城市 / 邮箱域名）？命中他人客户时返回什么（只说「已存在」还是披露归属人）？
- 建议默认：根域名优先、税号次之、名称+城市兜底；**命中他人客户时只返回「已存在，已通知归属人」，不披露对方资料**。

## D3 「公司有效」与「可邮件触达」的判定

- 需要定：MX 只作弱信号（不是邮箱存在证明）；无邮箱公司保留；联系人不猜造。
- 建议默认：公司有效性看「有官网 + 有可核验的经营信息」；可触达看「有员工可见的联系邮箱 + 未退订 + 未抑制」，两者分开存字段。

## D4 额度模型

- 需要定：额度层级（公司/部门/员工/任务）、预留与回收时机、超额是拒绝还是排队。
- 建议默认：四层都能设上限，实际可用 = 四层最小值；任务创建时预留，Run 结束按实际消耗结算，超时未启动全额回收。

## D5 审批与发送的职责分离

- 需要定：谁能批准（直属主管 / 部门管理员 / 群发需双人）？批准后改内容是否重新审批？发送状态未知怎么办？
- 建议默认：直属主管批单发、部门管理员批群发；批准后任何收件人/附件/正文变更一律回退重审；状态未知先查询再决定，不盲重试。

## D6 离职/转交规则

- 需要定：客户归属转移给谁（主管指定 / 部门池）、在途任务与草稿怎么处理、助手与 Bot 何时解绑。
- 建议默认：离职即冻结该员工助手与 Bot 绑定，归属转部门池待主管指派，在途 Run 取消并记账，草稿转交。

## D7 入口收敛的骨架

- 需要定：是否采用「工作台 / 客户开发 / 销售业务 / 资料中心 / 管理后台」五分区。M1 会先用现行模块声明核对，不会靠排除法归类。
- 建议默认：以核对结果为准；**如果某个分区没有承载条目，就不建这个分区**（菜单数由条目决定，不由设计稿决定）。

## D8 真实外发通道与域名

- 需要定：用哪个通道（resend / ses / 企业邮箱 SMTP）、发信域名、退订与投诉处理责任方。
- 现状：`channel-*` 包已安装但**未获真实外发授权**；M6 在批准前只做草稿与本地回执模拟。
- 建议默认：先在一个子域做认证与预热，只对内部测试地址发送，通过后才谈真实客户。

## D9 DSH 隔离形态

- 需要定：DSH 与 CRM 同机不同容器，还是独立主机？共享实例还是每员工一实例？
- 建议默认：先每员工独立 profile + 独立数据目录（同机），验证隔离证据后再谈共享实例降本；**共享实例不可信就隔离，不靠隐藏按钮冒充安全**。

## D10 试用范围

- 需要定：哪几个业务员/主管、试用时长、并行 Run 上限、出问题谁拍板停。
- 建议默认：2 业务员 + 1 主管，两周，并行 Run ≤ 员工数 × 2，出现任一安全用例失败立即停。

## D11 设置首页的权威版本

- 现状：`/backend/settings` 是 stock 占位页（815 byte），`/backend/config/home` 是应用自建的卡片网格；两者 `navHidden`，设置按钮写死指向占位页；`settings_home/index.ts` 声称的 `auth` override 在 `src/modules.ts` 里不存在。
- 建议默认：**`/backend/config/home` 为权威**，`/backend/settings` 改 301 指过去，并删掉那句假注释。

## D12 v2 客户详情页（`people-v2/[id]`、`companies-v2/[id]`）

- 现状：全仓无入链，无 feature flag，无法从代码判断是替代还是灰度。
- 建议默认：若确认是替代，收编为唯一详情页并给 v1 路径 301；若不替代，删除，避免两套实现同时演进。

## D13 导航基线口径

- 定：以 `node scripts/crm-nav-baseline.mjs` 产出的服务端 payload 快照为验收基线（superadmin/admin/employee 三份），**任何导航改动必须重跑并 diff**，不接受「我看菜单少了」这类口述。

## D14 业务员首页

- 现状：`/backend` 是通用仪表盘，无角色维度。
- 需要定：是给业务员一个独立首页路由，还是按角色在同一路由下渲染不同卡片。
- 建议默认：同一路由按角色渲染（避免多一个入口），但数据范围必须是「本人 + 授权范围」。

## D15 部分唯一索引只能手写，用演练白名单守住

- 现状：leadgen 有 4 条带 `where` 的部分唯一索引（同一员工仅一条 active 绑定、同一地址仅一条 active 抑制、同一渠道身份仅一条 active Bot 绑定、同一候选仅一次 CRM 入库）。MikroORM 7.2.5 的 `IndexOptions` **没有** `where` 字段，装饰器表达不了，所以它们只存在于迁移 SQL、不在实体快照里。
- 已实测：对已应用的 schema 跑 `yarn mercato db generate`，输出 `leadgen: no changes`——常规生成**不会**删掉它们。
- 定：接受"手写 + 白名单 + 每次复核"这条路。`scripts/crm-migration-drill.mjs` 里的 `PARTIAL_UNIQUE_INDEXES` 是唯一登记处，逐条断言列与谓词；出现未登记的手写索引，演练门直接红。
- 代价说清楚：新增同类索引必须同时改两处（迁移 + 白名单），漏了会红而不是静默通过。这是有意的摩擦。

## D23 恢复演练要比"结构 + 内容"，而且先证明比对器会红

- 现状：第 25 轮的演练只比 `information_schema.tables` 计数和 6 个 `count(*)`。这份判据在"索引全丢、外键全丢、序列全丢、某一行值被改"四种情况下都返回 PASS——行数与表名恰好是最容易幸存的两样东西。
- 定：结构比对落在 `scripts/lib/catalog-digest.mjs`，摘要覆盖列（名称/类型/长度/可空/默认/逻辑序）、索引（名字 + 完整定义）、约束（类型/表/列集合/外键目标/级联动作/可延迟）、序列、触发器、视图；探针表另做"行数 + 整表内容摘要"。
- 定：**每次演练先跑比对器的反向自证**——两个 schema 建同构 DDL 必须比出 0 差异，再逐一注入四种差异（多索引/多列/丢序列/丢外键）并要求各自被点名。没见过红的比对只是一句注释。
- 两处判据边界写进结果里，不当成证明：
  1. 列序用 `row_number()` 排行序号，不用物理 `ordinal_position`——源库 `DROP COLUMN` 留下的 attnum 空洞不会被重建复现，比物理序号会把"正常恢复"判红。
  2. CHECK 约束比存在、名字与列集合，**不比谓词文本**——pg_dump 的 deparse 往返会把等价表达式改写成另一种形态（实测 `ANY ((ARRAY[...])::text[])` → `ANY (ARRAY[(...)::text, ...])`），比文本会报一个不存在的差异。
- 反向证据：删掉真实的 `sales_quotes_acceptance_token_unique` → 点名缺失索引（连 `CREATE UNIQUE INDEX` 定义）与约束；改一行 `users.email`（行数 3→3 不变）→ 内容摘要不同被判红。旧实现两种都放行。

## D24 verify-all 的报告必须自带证据

- 现状：PASS 行 `note` 恒为空字符串，报告只记"通过"两个字；报告头也不记工作树状态，于是"这份报告证明的是哪个提交"无从判断。
- 定：每个 PASS 行写入该门禁自己 stdout 里的摘要行（门禁可用 `evidence: /re/` 指名要哪一行，否则取最后一条非 `RESULT:` 行）；报告头始终记录工作树干净/脏及未提交项。
- 定：`--require-clean` 为发布级开关，脏树直接判失败；`--require-no-skip` 仍然生效。两者一起用才是"提交级证据"。
- 定：跳过项永远不计入通过，这条不变。
- 定（第 49 轮补）：`--only` 子集运行必须在报告里留痕——标题写"子集验证结果（不是全量）"，头一行写 `范围：仅 <ids>（N/22 道门，不是全量）`。之前子集报告与全量报告长得一模一样，都被叫"全量验证结果"，可以原样被引用成全量通过。
- 定（第 49 轮补）：变异门的锚点必须**唯一**。`replace` 只改第一处，锚点重复时可能改的是注释或另一个分支，被测代码原样不动——这种情况判 INVALID 而不是 SURVIVED，因为它对 `why` 说的那条行为什么也没证明。现有 12 条锚点实测均唯一。

## D25 每员工 DSH profile 的派生规则与边界

- 现状：03 契约 §5 要求"每员工独立 profile"（会话/产物/记忆/浏览器/凭据），但仓里没有任何代码派生这个对象——隔离只是文档属性。
- 定：`src/lib/dsh/profile.ts` 是唯一派生处，纯函数、同一输入同一结果（可事后审计）。工具集 = 运行时报告的已授权工具 ∩ 助手上限 ∩ 调用方请求；越界请求**不静默裁掉**，进 `dropped` 并带原因（`not-in-assistant-ceiling` / `not-granted` / `outside-request`）。
- 定：四个根目录用身份元组的 sha256 前 32 位做 key。**路径里不出现任何 userId**，包括本人的——泄露面比"只含自己的 id"更小，且便于断言。
- 定：`wideningAttempt(parent, child)` 返回子集里父集没有的工具，**不自动修剪**。子 agent 请求父集外的工具是提权尝试，要能被记录，而不是被悄悄纠正。
- 定：`revoke()` 失败关闭：工具清零、`revoked=true`、身份保留（审计还要能定位到人）。
- 为什么不是"框架已经保证了子集"：`AiAgentExtension` 有 `appendAllowedTools` 与 `replaceAllowedTools`，注册表本身**不做**子集校验（实测：`src/modules/example/ai-agents.ts` 声明的扩展给 `customers.account_assistant` 追加了一个工具）。交集必须在这里发生，不能假设上游会做。
- 边界写清楚：本层只证"名字是对的"。DSH 是否按这些根目录隔离、运行中的子 agent 是否触达不到 profile 外的工具、文件系统权限是否互不可读——**都未证**，M4 用例 4/6 的运行时部分仍 blocked。

## D26 profile 要真的落到磁盘，权限位本身就是机制

- 现状（46 轮止）：派生层只产出字符串路径，目录从未被创建；"互不可读"没有任何实测。
- 定：`materializeProfile(profile, root)` 负责落盘——四个目录`0700`（`mkdir` 的 mode 会被 umask 掩掉，所以显式 `chmod`）、`profile.json` `0600`。目录已存在且元数据属于另一个身份时**抛错并拒绝复用**：哈希碰撞、复制粘贴、快照回滚都不该静默变成两个员工共用一个会话根。
- 定：门里做**跨 OS 用户**读测试（`sudo -n -u postgres cat <pro 的 profile>`），并且必须满足三条才叫证明：
  1. 拒绝原因是 `Permission denied`（EACCES），不是"文件不存在"或"sudo 没配"——否则一个拼错的路径也能"通过"；
  2. 同一棵临时树里放一个 `0644` 控制文件，`postgres` 必须能读到——证明拒绝来自权限位而不是根目录本身不可达；
  3. 根目录 `chmod 0711`：`mkdtemp` 默认 `0700` 会把陌生人在根目录就挡住，那样下面每一条拒绝都无法归因。
- 反向证据：`probe-reads-same-tree` 第一次跑就失败——控制文件读不到，因为根目录还是 0700。**阳性对照先抓住了我自己的假阴性。**
- 边界：这只证明"这台机器上 `pro` 与 `postgres` 之间的权限位有效"。生产上服务账号、容器边界、挂载参数都可能不同，那条要等发布前用真实运行态复验。

## D27 发布级判定的口径（第 48 轮 QA 后收紧）

- 定：报告头必须记**完整 flags**、`发布级：是/否`，汇总行必须给 `发布级门禁：PASS/FAIL`。只靠退出码判断"这是不是提交级证据"，读者看报告时无从得知。
- 定：`--only` 与 `--require-clean`/`--require-no-skip` **同用即拒绝**。子集运行不是发布级证据；不跑的门就是没人看的门，不能靠"没记 SKIP"来绕过"SKIP 不计入通过"。
- 定：`git status` 读不到时，`--require-clean` 按**不干净**处理（"无从判断"不是"干净"）。
- 定：运行前后各取一次工作树快照。门产物（`docs/crm-platform/{verify,poc,regression}/`）与人工改动**分开计数**；发布级下人工改动不为 0 即失败。这样"报告说干净"描述的是整次运行，而不只是启动那一秒。
- 定：门禁的证据行必须**自带它声称的属性**。例如恢复演练新增 `summary` 行（结构 N 列/索引/约束/序列 + 探测表内容摘要），profile 门的 `RESULT` 行写明"目录 0700、陌生人读不到"。之前证据行只挑到 `compare.catalog` 或"2 个角色"，读者引用那一行时会高估。

## D28 报价回归门需要一条 draft 报价夹具，而这条夹具会被业务动作吃掉

- 现状：`crm-quote-regression` 用 `select id from sales_quotes where status = 'draft'` 找夹具。2026-11-09 03:17:33 一次 `sales.order` 写入之后，表里只剩一条 `status = NULL` 的报价（`<null>=1`），门于是失败。这不是报价修复回归，是夹具没了。
- 定：门失败时必须打印 `status` 分布与两条可行路径（`--quote <uuid>` 或自建夹具），不能只丢一句 `cannot resolve a draft quote`。本轮已实现。
- 定：**不把 `status IS NULL` 当成 draft**。那行报价没有状态条目，把它当草稿去跑 convert/send 是在猜；门宁可不跑。
- 定：**不让这个门在缺夹具时静默跳过**。跳过不计入通过（`--require-no-skip` 会红），缺夹具就红，红得可解释。
- 待批：允许脚本自建夹具——`POST /api/sales/quotes` 建一条最小草稿 → 跑回归 → `DELETE` 撤销。属数据写入，需用户明确同意后实现；在此之前，发布级运行需要有人手工提供 `--quote`。

## D29 Bot 入站的门禁顺序是安全属性，不是实现细节

- 定：顺序固定为 **验签+时效 → 记 nonce → 重放 → 身份 → 群聊/脱敏**（`src/lib/bot/inbound.ts`）。
- 定：`rememberNonce` 只在签名与时效都通过之后调用。否则未认证请求可以烧 nonce（撑大 ledger、并把合法消息判成重放）。
- 定：认证通过但被后续门拒绝的消息**仍然记 nonce**。它已被认证，允许无限重试才是漏洞。
- 定：重放检查在身份之前。否则被撤销的绑定会掩盖重放，且拒绝原因泄露"该身份已撤销"。
- 定：群聊只允许 `read`，且离开 CRM 的文本必须过 `redactForGroup()`；单聊不脱敏。放行项由调用方显式列出，不默认放行。
- 这些顺序各有一条测试和一条变异守护，改动顺序会红。

## D30 撤权要分两半：取消广播 ≠ 写入被拦住

- 定：`applyPrincipalRevoked()` 只做账——把在途 Run 转 `cancelled`；`canWriteToCrm()` 才是最后一道闸，在**写入当时**按 run 状态 + 绑定状态判定。
- 为什么分开：取消广播是异步的，run 对象上可能还写着 `running`。把绑定状态作为参数传进写入门，才能关掉这个时间差；从 run 上读绑定状态等于假设广播已经到达。
- 定：`queued` 与 `awaiting_approval` 都算在途，但都**不能写**。等审批的 Run 被撤权后如果还能"恢复"并写入，撤权就形同虚设。
- 定：`applyPrincipalRevoked()` 不碰已终结的 Run（completed/failed/budget_exhausted），也不碰别的绑定，只对别的绑定计数。
- 定：10 s 是硬判据：`withinRevocationDeadline()` 对"取消早于撤销"和"缺时间戳"都返回 false，不把不可判当成合规。

## D31 工具授权三类由注册表元数据算出来，不靠人工分类

- 定：`high_privilege` = `isDestructive` ∪ `isBulk` ∪ 无 `requiredFeatures`。前两个能一次影响多行或不可撤销，第三个是"任何登录用户都能调"——三者都不该出现在共享实例里。
- 定：`instance_global` 只能**显式声明**（`docs/crm-platform/appendix/tool-policy.json`），因为"作用是否限于调用者"无法从元数据可靠推断，猜比承认不知道更糟。
- 定：声明不能把高权限降级——先算高权限，再看声明。
- 定：门做**双向**核对。只做单向（漏声明即红）会积累僵尸条目：工具改名/删除后声明还挂着，读的人会以为它还在。
