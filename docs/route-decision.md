# 路线判定：Fork 包源码（A′）vs 独立前端（B）

判定对象是「报价→订单」这条闭环所需的改动能不能落在应用层。结论先给：**走 A′（vendor 源码构建），B 只作为长期可选项保留，不在本轮启动**。下面是量出来的依据，不是偏好。

## 判定用的四个事实

| 事实 | 数值 / 证据 | 来源 |
| --- | --- | --- |
| 应用层没有页面渲染权 | `src/app/(backend)/backend/[...slug]/page.tsx` 一个 catch-all 渲染全部后台页；`src/app` 自写 page 仅 6 个 | 目录清点 |
| 应用层没有格式化权 | 销售表格的金额/日期在 `@open-mercato/core` 里内联格式化：`NumberFormat(void 0` 23 个文件、`toLocaleString()` 136 个文件、`toLocaleDateString()` 60 个文件 | 全仓 grep |
| 应用层没有写语义权 | `convert_to_order` 缺状态前置条件；`sales_orders` 无 quote 回指列 | 实测 200 + 表结构 |
| 服务端 API 边界是真的 | OpenAPI 676 path / 1149 op，认证态 11.25 MB，匿名 401 | `/api/docs/openapi` |

## 两条路线的真实成本

| 维度 | A′：fork 包源码并 vendor | B：独立前端调用 API |
| --- | --- | --- |
| 页面渲染 | 直接改 TSX，1 次构建 | 重写全部页面，且要自己实现表格/权限/组织范围 |
| 格式化 | 改 `format.ts` 一处 + 删除 shim | 自己格式化，但列表数据仍来自包的路由，字段语义要对齐 |
| 写语义 | 改 command，天然覆盖 UI 与 API | 前端挡不住 API 直调，服务端仍是漏的 |
| 权限可见性 | 已有 `requireFeatures` 过滤，无需重做 | 要重新实现同一套 feature 校验 |
| 交付周期 | 已有 mirror 与构建脚本（`packages/ui` 5.3s 构建通过） | 至少是「重写 40 个导航项对应页面」的量级 |
| 风险 | 与上游 diff 需持续维护 | 双份权限/双份审计，长期分叉 |

## 为什么 B 现在不成立

B 的前提是「API 足够完备，前端可以完全脱离」。API 确实完备（676/1149），但 **B 解决不了本轮发现的三个缺陷**：

1. `convert_to_order` 不校验状态——前端不调它，别的客户端照样能调；只有服务端能修。
2. 金额/日期格式在服务端渲染的 RSC 载荷里就已经定型，独立前端要么重写数据投影，要么接受同样的错。
3. nav 的 `requireFeatures` 过滤发生在包内；B 要把这套逻辑再实现一遍，等于把同一份规则维护两次。

换句话说：B 是「另建一套」，A′ 是「把这一套修好」。当前缺陷密度（3 个都在包里）指向 A′。

## A′ 的收敛路径

1. 用已存在的 mirror（`ctomall/open-mercato`）承载 `packages/*` 源码改动，构建产物 vendor 进 `ila3-commerce`。
2. 依次把受管补丁搬进源码：`format-locale` → `quote-transition-guard` → `dictionary-control-chars` → `numeric-columns` → 导航相关。
3. 每搬一个，补丁数 -1；补丁降到 0 时，`verify-patches` 只剩「无补丁」这一条断言。
4. 应用层只保留真正的产品代码（页面、组件、i18n、nav 数据）。

## 本轮不启动 B 的条件

只有出现下列情况才值得重估 B：需要多端复用同一套 API（例如卖家 App）、或包的上游维护停摆且 fork 成本超过重写。目前两者都不成立。

## 与单页重设计的关系

重设计选哪一页都走 A′：页面在包里，改包才能改页面结构。首屏验收建议选「报价单列表 → 报价单详情」，因为这一页同时承载格式化、状态、权限三个已修/待修点。
