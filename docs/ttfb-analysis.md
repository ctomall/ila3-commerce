# 公网 TTFB 实测与口径分析（2026-11-05）

## 结论先行

| 口径 | TTFB | 与目标 ≤0.8s |
|---|---|---|
| 浏览器（HTTP/3，连接复用，n=6） | p50 **0.440s** / p95 **0.448s** | ✅ 达成 |
| curl 单连接复用第二次请求（n=3） | 0.465–0.481s | ✅ 达成 |
| curl 每次新建连接（n=20） | p50 0.878s / p95 **0.901s** | ❌ 超出 |
| 源站本机处理 | **0.034s** | — |

**结论：面向真实用户的 TTFB 已达标（0.448s），之前记录的 1.79s 是"冷连接 + 链路拥塞"窗口下的孤立样本。**

## 为什么两种口径差一倍

```
冷连接：TCP 握手(0.20s) + TLS 1.3(0.20s) + 首个请求响应(0.45s) ≈ 0.85–0.9s
热连接：                           首个请求响应(0.44s) ≈ 0.44s
```

`time_connect` 实测 **0.200s**（到 Cloudflare 边缘），正好等于一个跨洋 RTT。
浏览器首次访问付一次握手成本，之后的导航/刷新全部复用连接。

## 为什么不是源站的问题

| 证据 | 数值 |
|---|---|
| 本机 `/login` TTFB | 0.034s |
| 边缘已缓存资源 `/brand.svg`（`cf-cache-status: REVALIDATED`） | p50 0.867s（**与 HTML 同级**） |
| `/login` 页面体积（优化后） | 104 KB |

连"边缘已缓存的小文件"都要 0.87s，说明这部分耗时是**连接建立与 RTT**，不是源站渲染、也不是页面大小。

## 若要进一步降低

| 手段 | 预期 | 前置条件 |
|---|---|---|
| 边缘缓存匿名页（Cache Rule + `s-maxage`） | 热连接下再降到 ~0.2s | **Cloudflare 账号权限**（应用侧改 `Cache-Control` 不足以让 CF 缓存 HTML） |
| Argo Smart Routing | 降低 RTT 抖动 | Cloudflare 付费功能 |
| 更近的出口/中继节点 | 冷启动从 0.9s 降到 ~0.4s | 预算 + 运维 |

## 建议的验收口径

- **主口径**：浏览器 warm TTFB p95 ≤ 0.8s → 当前 **0.448s**，通过；
- **辅口径**：冷启动（首次访问）TTFB ≤ 1.2s → 当前 0.85–0.92s，通过；
- 不建议用「每次新建连接的 curl」作为验收口径——它把一次性的握手成本计入每一次请求。
